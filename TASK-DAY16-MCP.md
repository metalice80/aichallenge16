# День 16. Подключение MCP: минимальный STDIO-клиент

## 1. Назначение задания

С нуля создать небольшое консольное приложение на Kotlin и Spring Boot, которое через официальный Java SDK протокола Model Context Protocol (MCP):

1. запускает тестовый MCP-сервер `@modelcontextprotocol/server-everything` как дочерний процесс через `npx`;
2. устанавливает с ним MCP-соединение по STDIO;
3. выполняет MCP `initialize`;
4. запрашивает `tools/list`;
5. выводит в лог сведения о сервере и список доступных инструментов;
6. корректно закрывает MCP-клиент и дочерний процесс;
7. подтверждает основной сценарий интеграционным smoke-тестом.

Результатом должен быть полностью собираемый и запускаемый проект, а не отдельный фрагмент кода.

## 2. Обязательный стек

- Kotlin;
- Spring Boot;
- Gradle Kotlin DSL (`build.gradle.kts`);
- JDK 21;
- официальный MCP Java SDK;
- синхронный MCP-клиент;
- STDIO transport;
- JUnit 5 для тестов;
- Node.js и `npx` только для запуска внешнего тестового MCP-сервера.

Зафиксировать версии: Spring Boot `4.1.1`, Kotlin `2.3.21` и MCP Java SDK `2.0.1`. Не использовать milestone, RC или snapshot-зависимости.

## 3. Предпосылки

На машине должны быть доступны:

- JDK 21;
- Node.js актуальной LTS-ветки, рекомендуется Node.js 20 или новее;
- `npx`, устанавливаемый вместе с npm/Node.js;
- доступ к Maven Central;
- доступ к npm registry при первом запуске `npx`.

Проверка окружения:

```bash
java -version
node --version
npx --version
```

Отдельно проверить тестовый сервер:

```bash
npx -y @modelcontextprotocol/server-everything
```

При ручном запуске сервер ожидает MCP-сообщения через stdin, поэтому отсутствие обычного приглашения или зависание в ожидании ввода является нормальным. Остановить его можно через `Ctrl+C`.

Глобально устанавливать `@modelcontextprotocol/server-everything` не требуется: ключ `-y` разрешает `npx` автоматически скачать отсутствующий пакет.

На Windows команда может называться `npx.cmd`. Команда запуска должна настраиваться через `application.yaml`, чтобы ее можно было заменить без изменения Kotlin-кода.

## 6. Gradle-конфигурация

Использовать плагины Spring Boot, Kotlin/JVM и Kotlin/Spring. Подключить Gradle Wrapper и toolchain для Java 21.

Минимально необходимые зависимости:

```kotlin
dependencies {
    implementation(platform("io.modelcontextprotocol.sdk:mcp-bom:2.0.1"))
    implementation("io.modelcontextprotocol.sdk:mcp")

    implementation("org.springframework.boot:spring-boot-starter")
    implementation("org.jetbrains.kotlin:kotlin-reflect")

    testImplementation("org.springframework.boot:spring-boot-starter-test")
}
```

Требования к сборке:

- использовать `mavenCentral()`;
- не подключать `spring-boot-starter-web`;
- не подключать Spring AI;
- не указывать разные версии отдельным MCP-модулям: их версии управляются одним BOM;
- включить JUnit Platform;
- компилировать Kotlin в JVM 21 через toolchain;
- не отключать тесты ради успешной сборки.

Модуль `mcp` — официальный агрегирующий модуль SDK: он подключает `mcp-core`, стандартные transport-реализации и JSON-сериализацию Jackson 3, совместимую с выбранной веткой Spring Boot 4. Не добавлять одновременно `mcp-json-jackson2` и не смешивать Jackson 2/Jackson 3.

## 7. Конфигурация приложения

Создать типизированные настройки с `@ConfigurationProperties`, например с префиксом `app.mcp`.

Обязательные свойства:

- `command` — исполняемая команда, по умолчанию `npx`;
- `arguments` — аргументы дочернего процесса;
- `request-timeout` — тайм-аут MCP-запросов;
- `demo-enabled` — включает демонстрационный runner.

Базовый `application.yaml`:

```yaml
spring:
  application:
    name: day16-mcp-client
  main:
    web-application-type: none

app:
  mcp:
    command: ${MCP_COMMAND:npx}
    arguments:
      - -y
      - "@modelcontextprotocol/server-everything"
    request-timeout: 20s
    demo-enabled: true

logging:
  level:
    root: INFO
    com.example.mcpday16: INFO
```

Требования:

- не зашивать команду и аргументы непосредственно в сервис;
- валидировать, что `command` и каждый аргумент не пусты;
- тайм-аут должен быть положительным;
- значения по умолчанию должны позволять запустить проект без дополнительной конфигурации на macOS/Linux при наличии `npx`;
- для полностью воспроизводимого CI разрешается закрепить точную опубликованную версию npm-пакета в конфигурации, но нельзя менять сам пакет на другой MCP-сервер.

## 8. Реализация MCP-клиента

### 8.1. Транспорт и клиент

Использовать API официального SDK версии `2.0.1`:

- `ServerParameters` для описания запускаемого процесса;
- `StdioClientTransport` для транспорта;
- `McpClient.sync(...)` и `McpSyncClient` для синхронного клиента;
- `McpJsonDefaults.getMapper()` для JSON mapper, предоставляемого официальным модулем SDK;
- `initialize()` для рукопожатия;
- `listTools()` для запроса инструментов;
- `closeGracefully()` для штатного закрытия.

Ориентир последовательности вызовов:

```kotlin
val serverParameters = ServerParameters.builder(properties.command)
    .args(*properties.arguments.toTypedArray())
    .build()

val transport = StdioClientTransport(
    serverParameters,
    McpJsonDefaults.getMapper(),
)

val client = McpClient.sync(transport)
    .requestTimeout(properties.requestTimeout)
    .build()

val initializeResult = client.initialize()
val toolsResult = client.listTools()
```

Это ориентир, а не код для слепого копирования: итоговая реализация должна использовать точные сигнатуры SDK `2.0.1` и успешно компилироваться.

### 8.2. Сервис

`McpClientService` должен:

1. получить типизированные свойства;
2. создать параметры дочернего процесса;
3. создать STDIO transport и синхронный MCP-клиент;
4. вызвать `initialize()` до любых других MCP-операций;
5. вызвать `listTools()` ровно после успешной инициализации;
6. преобразовать ответ в небольшой внутренний результат, не протаскивая SDK-типы в runner без необходимости;
7. вернуть как минимум:
   - согласованную версию протокола;
   - имя и версию сервера, если сервер их вернул;
   - список инструментов с именем и описанием;
8. гарантированно вызвать `closeGracefully()` в `finally`;
9. обеспечить резервное идемпотентное закрытие при остановке Spring-контекста;
10. при ошибке записать одно содержательное сообщение и пробросить исключение с исходной причиной.

Не скрывать ошибку соединения и не возвращать пустой список как будто операция была успешной. Не использовать `exitProcess` внутри сервиса.

В штатном и аварийном сценариях после завершения приложения не должен оставаться дочерний процесс `server-everything`.

### 8.3. Модель результата

Создать собственные простые Kotlin-модели, например:

```kotlin
data class McpDiscoveryResult(
    val protocolVersion: String,
    val serverName: String,
    val serverVersion: String?,
    val tools: List<McpToolSummary>,
)

data class McpToolSummary(
    val name: String,
    val description: String?,
)
```

Допустима другая форма, если она сохраняет перечисленные данные.

### 8.4. Runner

Создать `ApplicationRunner` или `CommandLineRunner`, который активен при `app.mcp.demo-enabled=true`.

Runner должен:

- однократно вызвать сервис при старте приложения;
- вывести результат через SLF4J, а не через `println`;
- не вызывать инструменты;
- не содержать деталей создания транспорта;
- не перехватывать ошибку так, чтобы приложение завершалось с кодом успеха;
- после окончания демонстрации позволить non-web приложению завершиться.

## 9. Логирование

В успешном сценарии лог должен ясно показывать:

1. начало подключения и имя запускаемой команды без секретных переменных окружения;
2. успешный `initialize`;
3. версию протокола;
4. имя и версию MCP-сервера, если доступны;
5. количество полученных инструментов;
6. для каждого инструмента — имя и краткое описание;
7. закрытие клиента.

Пример формы лога, точный текст не обязателен:

```text
Connecting to MCP server via STDIO: npx
MCP initialized: protocol=..., server=... (...)
MCP tools received: count=...
MCP tool: name=echo, description=...
MCP client closed
```

Не логировать:

- полный набор переменных окружения дочернего процесса;
- секреты;
- сырые JSON-RPC сообщения на уровне INFO;
- огромные JSON Schema целиком;
- stack trace дважды на разных слоях.

Важно: stdout дочернего MCP-процесса является каналом протокола. Не пытаться самостоятельно читать его параллельно с `StdioClientTransport` и не смешивать с пользовательским консольным выводом.

## 10. Обработка ошибок

Должны быть понятны как минимум следующие ситуации:

- `npx` отсутствует или недоступен через `PATH`;
- npm-пакет невозможно скачать;
- MCP-сервер завершился до `initialize`;
- истек тайм-аут;
- `initialize` завершился ошибкой;
- `tools/list` завершился ошибкой;
- закрытие клиента завершилось ошибкой.

Для основной ошибки сохранять исходный stack trace/cause. Ошибка закрытия не должна затирать первоначальную ошибку; ее следует записать отдельно или добавить как suppressed exception.

При невозможности выполнить основной сценарий приложение должно завершиться неуспешно.

## 11. Тестирование

### 11.1. Интеграционный smoke-тест

Обязателен тест, который использует реальный `npx` и реальный `@modelcontextprotocol/server-everything`, а не mock транспорта.

Тест должен:

1. быть помечен JUnit-тегом `integration`;
2. запускать Spring-контекст либо производственный `McpClientService` с реальной конфигурацией;
3. отключать демонстрационный runner через `app.mcp.demo-enabled=false`, чтобы сервер не запускался дважды;
4. выполнить production-путь `initialize` → `tools/list`;
5. проверить, что версия протокола непустая;
6. проверить, что сведения о сервере получены;
7. проверить, что список инструментов не пуст;
8. проверить, что имена всех инструментов непустые;
9. не проверять точное число инструментов и полный фиксированный набор имен, поскольку тестовый сервер может развиваться;
10. гарантированно закрыть клиент даже при падении assertion;
11. иметь разумный тайм-аут, чтобы зависший дочерний процесс не блокировал сборку бесконечно.

Если `npx` отсутствует, интеграционная задача должна завершаться с понятной ошибкой о невыполненной предпосылке, а не молча пропускать тест и создавать ложное впечатление успешной проверки.

### 11.2. Gradle-задачи тестов

Разделить быстрые тесты и внешний smoke-тест:

- стандартная задача `test` исключает тег `integration`;
- отдельная задача `integrationTest` включает тег `integration`;
- интеграционный тест не должен запускаться параллельно сам с собой;
- команда `./gradlew integrationTest` должна работать без ручного запуска сервера: сервер запускает сам SDK через STDIO.

Не обязательно привязывать `integrationTest` к `check`, поскольку он требует Node.js и сети при первом скачивании npm-пакета. В критериях приемки обе задачи запускаются явно.

## 15. Ограничения реализации

- Сохранять решение минимальным и учебным.
- Не заменять реальную интеграцию mock-объектами в smoke-тесте.
- Не запускать `npx` вручную через отдельный `ProcessBuilder` параллельно SDK: процесс должен создавать `StdioClientTransport` на основании `ServerParameters`.
- Не выполнять shell-команду одной строкой через `sh -c`; передавать команду и аргументы раздельно.
- Не использовать абсолютные пути, специфичные для машины разработчика.
- Не хранить зависимости или содержимое npm-кэша в репозитории.
- Не коммитить `build/`, `.gradle/`, `node_modules/`, IDE-файлы и логи.
- Не добавлять функциональность «на будущее», не требуемую этим заданием.
